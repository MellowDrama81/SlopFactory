# Architecture

## Projects

| Project | Responsibility |
|---|---|
| `Mellow.SlopFactory.Core` | Platform-neutral domain records, validation rules, exceptions, and workspace contracts |
| `Mellow.SlopFactory.Infrastructure` | SQLite persistence, manifests, exclusive locks, hashing, media-type detection, managed file operations, and the workspace implementation |
| `Mellow.SlopFactory.Gui` | .NET MAUI Blazor Hybrid shell and user interface for Windows and Android |
| `Mellow.SlopFactory.Tests` | Cross-platform domain and infrastructure tests running on `net10.0` |

The GUI depends on the application contracts rather than SQLite directly. `LibraryWorkspaceFactory` is registered through dependency injection as `ILibraryWorkspaceFactory`.

## Platform targets

- Windows: `net10.0-windows10.0.19041.0`
- Android: `net10.0-android`, with API level 26 as the minimum supported platform version

The development package identifier is `com.mellow.slopfactory.dev`, keeping development storage separate from a future production identity.

`LibraryLocationService` supplies the platform storage policy. Windows accepts absolute paths on non-network drives. Android enumerates only the process's internal and external app-specific directories. `AppLibraryState` persists the last successfully opened path in device preferences and swaps workspaces only after the replacement library has opened successfully.

The recent-library registry is device-local Preferences JSON, not part of any library. Entries contain the persistent library ID, display name, absolute platform location, stable storage-volume identity, last-opened UTC time, availability state, and only a sanitized open stage/diagnostic ID when corrupt. A successful validated open replaces stale path/name data for that ID. Switching rejects known ancestor/descendant ownership overlaps. If another registered path with the same ID remains available, opening the copy is rejected; if the old path is unavailable, selecting the new path relinks the registry without modifying the library ID. Forgetting removes the registry entry and that ID's preview cache only.

`IncomingImportService` bridges platform activation into Blazor without importing implicitly. Android `SEND`/`SEND_MULTIPLE` intents copy read-only content streams into a private random cache directory immediately, then release the provider grant. Windows file activation and native WebView drag/drop enqueue validated regular local paths; dropped directory enumeration is capped at 64 levels and 100,000 files and excludes hidden or reparse-point entries. Each dropped file carries a relative folder path, which the confirmed operation resolves into existing or newly created virtual folders below the reviewed destination. The memory queue survives page navigation, exposes a global review banner, and reports sanitized provider/enumeration failures. The Library page drains it into the ordinary import review. Temporary shared copies are deleted on removal, review cancellation, or completion; orphan staging directories from a terminated process are deleted on the next service startup.

## Library workspace lifecycle

`ILibraryWorkspaceFactory.CreateAsync` initializes an empty directory. `OpenAsync` accepts only a manifest/database pair with matching identity and schema information. Both return an `ILibraryWorkspace`, which owns an exclusive lock for its lifetime and must be asynchronously disposed.

Opening validates that the root, manifest, database, managed-media directory, and staging directory are the required regular entry types and are not reparse-point redirections. The root is checked before manifest access, required entries are checked before locking/database work, and managed directories are checked again after obtaining the exclusive lock. Individual managed-path access also rejects directories and reparse points.

The workspace is the atomic application boundary for folder browsing, imports, file and folder rename/move operations, bounded text and verified image reads, edited-copy commits, metadata, link creation/relabel/reversal, recycle/restore, and permanent file deletion. Multi-file move, recycle, metadata-set, and metadata-remove calls hold this boundary for the complete batch, while each selected file uses its own database transaction and produces an independent sanitized outcome. Invalid or duplicate selections are rejected before processing. Folder moves validate the complete descendant chain before updating the parent identifier; display-only organization never changes a file's internal managed name or byte location.

The built-in text reader accepts strict UTF-8 with or without its byte-order mark. Invalid UTF-8 and UTF-16 byte-order marks are rejected with a user-facing validation error. UI display is capped at 1,048,576 characters as a memory-safety boundary, not as a library storage limit.

The inline raster reader accepts PNG, JPEG, WebP, and GIF records up to 32 MiB. It reads only an active managed file and verifies its byte count and SHA-256 digest against the database before returning bytes to the WebView. The size boundary limits transient base64 and WebView memory; it is not a library storage quota.

SVG uses the same raw-byte verification before a strict XML sanitizer creates the viewing representation. DTDs and external XML resolution are prohibited. A small allowlist retains passive SVG geometry, text, definitions, gradients, masks, patterns, markers, symbols, and local fragment reuse; active elements, foreign namespaces, event attributes, style attributes, external links, and external CSS URLs are removed. The unsanitized SVG is never sent to the WebView.

Audio/video playback is capability-scoped rather than path-based. The workspace first validates an active playable record, a regular non-reparse managed file, byte size, and complete SHA-256 digest. The GUI then creates a random 256-bit session grant and gives HTML media controls only a same-origin `/slopfactory-media/<token>` address. `BlazorWebView.WebResourceRequested` intercepts that address, accepts only `GET` and `HEAD`, implements one bounded HTTP byte range with `200`, `206`, or `416` semantics, and opens a non-seekable length-limited stream. It returns `nosniff` and `no-store` headers and never discloses a managed path. Grants are bound to a library ID and content hash and are revoked when the component reloads or is disposed. JavaScript coordinates one active player, playback rate, and teardown; no media is autoplayed.

Raster viewing also performs header-level safety validation before WebView decode: dimensions are capped at 16,384 per axis and 100 million total pixels, while GIF frame count and estimated decoded animation memory are bounded. Exceeding a limit rejects only the preview and does not change the record or bytes.
Animated GIFs use the cached static thumbnail as their initial and paused representation. The original animated data URI is not attached to the DOM until the user explicitly plays it, and navigation restores the paused representation.

`PreviewCacheService` stores PNG thumbnails outside libraries under MAUI's device cache directory. Cache identities hash library ID, content hash, preview type, target size, and renderer version. Two workers generate previews on demand; raster images use MAUI Graphics and MP4 posters use `StorageFile` thumbnails on Windows or `MediaMetadataRetriever` on Android. A cache hit advances its filesystem LRU time. A device-wide 64 MiBâ€“8 GiB preference defaults to 1 GiB on Windows and 256 MiB on Android; writes and limit changes evict oldest entries. Cache status and explicit clearing are exposed in Library settings. Cache files contain no authoritative data and can disappear normally.

`ManagedContentWatchService` watches only the active library's top-level managed-media directory. It restarts on library switches, debounces per opaque managed filename, ignores paths without active records, and routes known records through workspace revalidation. Healthy expected import/copy events clear silently; missing or changed results become global review notices. An overflow or inaccessible revalidation produces only a full-scan recommendation. The watcher is advisory and never follows directories, accepts bytes, deletes content, or replaces the explicit verification performed by viewers and integrity scans.

The watcher also performs a low-frequency availability probe using the remembered stable volume identity and required writable atomic operations. An unavailable or read-only active library is detached safely while its registry entry remains. An entry closed specifically for unavailable Android storage is reopened only after the same volume and library validate again; corrupt entries are never auto-repaired or auto-opened.

The same service uses a separate root watcher for the manifest and primary SQLite file. Each critical event invokes `ValidateOpenLibraryAsync`, which acquires the workspace mutation gate, revalidates required entries, exact in-memory manifest and descriptor identity, and SQLite integrity. Failure asks `AppLibraryState` to atomically detach and dispose only that expected workspace while retaining its path and an actionable unavailable-library message. A stale watcher callback cannot close a subsequently selected library.

## Connections, models, and provider adapters

`Connection` and `Model` are library-scoped domain records (schema v9) exposed through `ILibraryWorkspace`, following the same active/recycled/pending-permanent-deletion lifecycle, label-uniqueness, and cascade conventions as folders and files: recycling a connection recycles its dependent models, and permanently deleting a connection permanently deletes those models. A connection's base URL is validated and normalized by `LibraryRules.NormalizeConnectionBaseUrl` (absolute `http`/`https`, no embedded credentials, HTTPS required for public hosts, HTTP allowed only for loopback/private-network hosts).

`IProviderAdapter` (Core/Application) defines `TestConnectionAsync` and `ListModelsAsync`. `OpenAiProviderAdapter` and `GenericOpenAiCompatibleProviderAdapter` (Infrastructure/Providers) implement it over a typed `HttpClient`, sharing request/response handling through `OpenAiCompatibleProtocol`. `IProviderAdapterResolver` resolves the adapter for a connection's `ProviderType` and is registered, along with the two adapters, by `AddSlopFactoryInfrastructure()`.

API keys are never stored in the library database. The GUI's `ISecureCredentialStore` (`MauiSecureCredentialStore`) wraps MAUI `SecureStorage`, keyed by library ID, connection ID, and (as of the revisioned credential lifecycle described below) a revision ID; the `Connection` record only stores a `HasCredential` flag plus a `CredentialRevisionId` pointer. The Connections and Models pages (`Components/Pages/Connections.razor`, `ConnectionEdit.razor`, `Models.razor`, `ModelEdit.razor`) call the resolved adapter directly for **Test Connection** and **Load Models**, and remove every stored credential revision when a connection is permanently deleted.

This is an initial slice of Milestone 2's connections-and-models scope; the remaining credential-lifecycle, capability-schema, and generation-workflow behavior is tracked in [milestone2.md](../../milestone2.md).

`ConnectionEdit.razor`'s `IsInsecureHttpBaseUrl` parses `_form.BaseUrl` live (independent of the save-time `LibraryRules` validation) and shows a warning the moment its scheme is `http`, since by the time an `http://` base URL is actually persisted, `NormalizeConnectionBaseUrl` has already guaranteed it is loopback/private-only — the warning exists purely so the user understands *why* before hitting save. `Connections.razor` shows the same warning as a short badge next to any already-saved connection whose stored `BaseUrl` starts with `http://`.

## Minimal text generation

`GenerationRecord` (schema v10: `generation_records`/`generation_results`) is a lightweight, synchronous generation-history record reached through `ILibraryWorkspace.RecordTextGenerationResultAsync`. It has none of the plan's full generation-lifecycle machinery (no async job polling, and no retries beyond the bounded model-listing case described below) — it exists to let a queued submission turn a prompt into library content end to end. See [Generation drafts and tabs](#generation-drafts-and-tabs) for the persisted draft/tab model, and [Generation queue and concurrency](#generation-queue-and-concurrency) for how submissions are now scheduled rather than run inline.

`IProviderAdapter.GenerateTextAsync` requests one or more chat-completion candidates (`OpenAiCompatibleProtocol.BuildChatCompletionRequestBody`/`ParseChatCompletionTexts`) from the OpenAI or generic adapter. The `/generate` page calls it directly, then calls `RecordTextGenerationResultAsync` with either the returned texts or a sanitized error message. `LibraryWorkspace.RecordTextGenerationResultCoreAsync` commits each text candidate as its own managed `.md` file (`FileOrigin.Generated`) using the same staging-write, hash, atomic-move sequence as `CreateEditedTextCopyAsync`, then records one `generation_records` row (model/provider snapshot, prompt, status, sanitized error) linked to its committed files through `generation_results`. A failed attempt (adapter threw) still commits a `Failed` history row with no files. `/generation-history` lists these records newest first.

`IProviderAdapter.GenerateImageAsync` requests base64-encoded image results (`OpenAiCompatibleProtocol.BuildImageGenerationRequestBody`/`ParseImageGenerationBytes`, POST `images/generations`, `response_format: b64_json`) and returns decoded byte arrays. `RecordImageGenerationResultCoreAsync` mirrors the text path but writes each image's bytes to staging first and detects its real media type/extension with `MediaTypeDetector.DetectAsync` (the same file-signature detector import uses) rather than trusting the provider's declared format, before the same atomic move and `InsertImportedFileAsync` commit. The `/generate` page offers one combined, mode-labelled model picker and branches to the text or image path based on the selected model's `GenerationMode`.

`generation_results.file_id` references `files(id)` `ON DELETE CASCADE` (schema v25 — previously it had no `ON DELETE` clause at all, so permanently deleting *any* generation-result file unconditionally threw a foreign-key `LibraryValidationException`, discovered while scoping the still-open generation-history recycle-bin item below). Deleting a result file now simply removes that one `generation_results` link row; the owning `GenerationRecord` stays intact with a correspondingly shorter `ResultFileIds`, mirroring how `source_file_id`'s existing `ON DELETE SET NULL` already clears a reference rather than cascading or blocking further. `GenerationRecord` itself still has no state/`recycled_at` lifecycle of its own — a history record cannot be recycled or permanently deleted; only its already-independent source/result files can be.

Everything else under Generation Inputs/Lifecycle/Results/History in `plan.md` — source inputs, prompt improvement, queues, audio/video results, provider result download/validation (status/content-type/checksum, unverified-binary retention), and recycle-bin integration for the history record itself (including file/source tombstoning, since neither source nor result files capture any former-identity data today) — remains open, tracked in [milestone2.md](../../milestone2.md).

## Saved generation settings

`SavedGenerationSetting` (schema v11: `saved_generation_settings`) is a title, model snapshot (ID plus label/mode, so a later-unavailable model still shows something meaningful), prompt, result count and destination folder, reached through `ILibraryWorkspace`'s saved-setting CRUD. It follows the same active/recycled/pending-permanent-deletion lifecycle and title-uniqueness convention as connections and models, and the same cascade shape: recycling a model recycles its dependent saved settings (and restoring/permanently deleting the model does the same in reverse), and recycling/restoring/permanently deleting a connection cascades through its models to their saved settings.

The `/generate` page (routed at both `/generate` and `/generate/{SettingsId}`) loads a saved setting's prompt/result-count/destination/model into its form when opened with an ID, and offers explicit **Save** and **Save As** actions (`SaveInPlaceAsync`/`SaveAsNewAsync`) instead of one button inferring intent from whether the typed title matches the loaded one. `/saved-settings` lists active and recycled saved settings with **Use** (opens `/generate/{id}`), recycle, restore and permanent delete.

A third route, `/generate/history/{HistoryId}`, backs a minimal **Use Again**: it loads a historical `GenerationRecord`'s prompt/result-count/destination/model into the same form without treating it as a saved setting (it never sets the loaded-settings/title state that makes **Save** update in place) and without altering the historical record itself. `/generation-history` links each entry to it.

## Saved-setting revision conflicts

Schema v24 adds `saved_generation_settings.revision`, an opaque counter starting at 1 and incremented on every successful `UpdateSavedSettingAsync` call. `Generate.razor` remembers the revision it last loaded or saved (`_loadedRevision`) and passes it as `UpdateSavedSettingAsync`'s new `expectedRevision` parameter; if the stored revision no longer matches, `SqliteLibraryDatabase` throws `SavedSettingRevisionConflictException` (carrying the current, authoritative record) instead of writing anything. This is a real, reachable scenario in this single-window app without needing multiple processes or devices: **Use** already opens the same saved setting into a *new* draft tab rather than replacing the page's only form state, so two tabs can independently load and edit the same saved setting, and the second one to click **Save** would otherwise silently discard the first tab's change with no warning.

`Generate.razor` shows **Save** (enabled only when a saved setting is loaded) and **Save As** (always available) as two separate actions rather than one button that guessed which behavior was wanted from a title comparison. On a conflict, a panel offers **Overwrite** (retries the update using the just-fetched current revision from the exception, which always succeeds since it is by construction the latest value), **Save As**, or **Cancel** — replacing what would otherwise have been an invisible last-write-wins overwrite.

The conflict panel also offers **Review Changes**, a `<details>` disclosure (the same pattern `GenerationHistoryDetail.razor` already uses for its collapsed system-instructions section) that field-diffs the current form/tab state against `SavedSettingRevisionConflictException.Current` — model label, prompt, system instructions, source image, destination folder path, and result count — and lists only the fields that actually differ as a read-only `<dl>`, never mutating either side. There is no dedicated "current draft as a `SavedGenerationSetting`" object anywhere in the code; `Generate.razor`'s `BuildConflictDiffRows()` assembles the "mine" side ad hoc from `_form`/`_settingsTitle`/`CurrentSavedSettingFields()` each time it renders, reusing the existing `FolderPath`/`SelectedModel` lookups (a source-file-to-display-name lookup, `ResolveSourceFileName`, was added alongside them, mirroring `FolderPath`'s own `UnknownFolder` fallback with a new `UnknownFile` one). This app has no `<table>` markup anywhere else, so the diff reuses the `<dl>` idiom `LibrarySettings.razor`'s Active Library panel already established rather than introducing one.

**Save** now also handles the source saved setting itself having been recycled or permanently deleted out from under an open tab, rather than surfacing only a generic validation-error message as before. `SaveInPlaceAsync` looks the source up (`workspace.GetSavedSettingAsync`, catching `RecordNotFoundException`) before attempting the update: gone entirely → the tab clears its `_loadedSettingsId`/`_loadedTitle`/`_loadedRevision` link (so only **Save As** remains offered — the existing UI already hides the **Save** button whenever nothing is loaded, so no new markup was needed for that half) and shows an explanatory message; merely recycled (`State != Active`) → a new `_settingsRecycledConflict` panel, shaped exactly like the revision-conflict one, offers **Restore and save** (`RestoreSavedSettingAsync` immediately followed by `UpdateSavedSettingAsync` with the tab's current values — a restore-blocked-by-title-conflict still surfaces as a plain `NameConflictException` message, no dedicated flow for that narrower edge case), **Save As**, or **Cancel**. Like the revision conflict itself, this is detected lazily at Save time rather than via any background watch. `SavedGenerationSettingTests` covers the domain sequence directly (recycle → restore → update in one flow; `RestoreSavedSettingAsync` throwing `NameConflictException` on a title collision and `RecordNotFoundException` once permanently deleted).

This deliberately does not cover a tab's own **model/source-file** dependencies (not the saved-settings record itself) becoming recycled or deleted — see below, which now covers the model half.

`LoadDraftIntoForm` (now `LoadDraftIntoFormAsync`) resolves a draft's stored `ModelId` against the already-loaded active-model list; a miss there is ambiguous by itself — recycled, permanently deleted, and merely-excluded-for-**Needs Review** are three different states that all just "aren't in `_models`". Converting the method to `async Task` (a safe, fully self-contained change — every one of its 9 call sites was already inside an `async Task` method, so this was a pure rename-and-await, not a wider refactor) lets it call `workspace.GetModelAsync(draft.ModelId)` on a miss and read the model's actual `LibraryRecordState` directly instead of guessing:

- **Recycled** — `GetModelAsync` returns the model with its label intact (recycling doesn't clear anything). A new `_recycledModel` field drives a specific notice ("model **X** was moved to the recycle bin") with an inline **Restore model** button calling `RestoreModelAsync` then a new `RefreshActiveModelsAsync(workspace)` helper (factored out of `OnInitializedAsync`'s own model-loading code, so both places stay in sync) to reload `_models` before re-selecting it. `RestoreModelAsync`'s own preconditions — the owning connection must already be active, and an active-label collision throws `NameConflictException` — surface through the existing generic `catch (SlopFactoryException)` pattern already used everywhere else in this file; no dedicated handling was added for either, matching how the saved-settings-source restore flow above also leaves its own restore-conflict class to the generic catch.
- **Permanently deleted** (`GetModelAsync` throws `RecordNotFoundException`) — unlike the recycled case, `_form.ModelId` is left **empty** rather than auto-falling-back to `_models[0]`. A new placeholder `<option value="">` renders only while `_form.ModelId` is empty, so the select visibly shows nothing chosen instead of silently landing on some other real model the user never picked; the **Generate** submit button gained `string.IsNullOrEmpty(_form.ModelId)` as an explicit disable condition, so submission is genuinely blocked until the user picks a replacement — this is the one case among all three where plan.md calls for blocking rather than a graceful fallback, since there is no way to guess what "replacement" means for a mandatory field.
- **Needs Review** (found, `State == Active`, but excluded from `_models` by the `!model.NeedsReview` filter) — unchanged: the pre-existing generic `DraftModelUnavailable` message and auto-fallback-to-`_models[0]` behavior, since this case has an obvious, harmless auto-resolution (the review flag doesn't mean the model is unavailable, just flagged) and isn't the scenario plan.md's restore/replace rules are about.

Source-image intentionally receives none of this — it already silently clears to "no source" when its file is recycled or deleted, and that was a deliberate, previously-documented choice (a secondary, non-blocking field, unlike the mandatory model), not an oversight being left unaddressed here. The prompt-improvement model select has the same established silent-fallback precedent and is likewise untouched.

## System instructions

Text-mode generation carries an optional **System Instructions** field (schema v12: `generation_records.system_instructions`, `saved_generation_settings.system_instructions`), shown on `/generate` only when the selected model's `GenerationMode` is `Text`. `OpenAiCompatibleProtocol.BuildChatCompletionRequestBody` writes it as the first message with the documented `system` role — never concatenated into the user prompt — and both adapters' `GenerateTextAsync` accept it as an optional parameter. It flows through `RecordTextGenerationResultAsync`, `CreateSavedSettingAsync`/`UpdateSavedSettingAsync`, saved-setting loading and **Use Again** the same way the prompt does; image generation never receives it. `/generation-history` shows it behind a collapsed `<details>` disclosure per record — a minimal stand-in for the documented reveal-and-clear-on-navigation behavior, not the full privacy mechanism.

## Token usage

`IProviderAdapter.GenerateTextAsync` returns a `TextGenerationResult` (texts plus optional `PromptTokens`/`CompletionTokens`) instead of a plain string list. `OpenAiCompatibleProtocol.ParseChatCompletionResult` reads the OpenAI-shaped `usage.prompt_tokens`/`usage.completion_tokens` fields when the provider includes them. `GenerationRecord` persists them (schema v13: `generation_records.prompt_tokens`/`completion_tokens`); `/generate`'s result panel and `/generation-history` show them when known. Only text generation captures usage this way — image generation, cost estimation and a cost-summary view remain open.

`/generate` also shows a pre-submission `LibraryRules.EstimateTokenCount` estimate (Text mode only) — a generic `~4 characters per token` heuristic applied to the combined system-instructions/prompt text, always labelled "rough estimate, not exact". This is a deliberately reduced stand-in for plan.md's much larger prompt/context-validation system (exact tokenizers, per-model context-window budgeting, a debounced **Estimating**/**Stale**/**Partial Validation** state machine that can block submission). Neither prerequisite for the "exact" half exists or is honestly buildable today: this app bundles no real tokenizer/vocab data, and no API it calls returns a model's actual context-window size — hardcoding one would assert unverifiable provider-specific facts, the same reasoning that already ruled out fabricating pricing data for the Cost-unknown notice. Because the estimate is instant arithmetic rather than an expensive real computation, there's also no debounced/cancellable background work or transitional state to build: `EstimatedTokenCount` is a plain computed property, recalculated live via `@bind:event="oninput"` on the prompt/system-instructions fields (previously plain `@bind`, which only commits on blur — this also makes `ScheduleAutosave` debounce while continuously typing rather than only after leaving the field). The estimate never disables or blocks **Generate**.

`/generate` shows a plain, always-visible **Cost unknown** notice (`Strings["CostUnknownNotice"]`) next to both the **Generate** submit button and the **Improve Prompt** action — a deliberately minimal stand-in for plan.md's much larger cost-estimation model (per-model/connection/pricing-revision acknowledgement tracking, confirmation thresholds, overrun highlighting). That machinery has nothing real to estimate from: no adapter exposes a provider cost-estimate API, and this project won't fabricate per-token/per-image pricing data to seed a bundled-pricing file instead. The notice is honest rather than silent about that gap, and requires no acknowledgement/dismissal state to track since there is no per-revision "cost unknown" concept without real pricing data to key it to.

## Vision source image

`/generate` offers one optional source image (from the active library's image-media files) when the selected model is Text-mode. `LibraryState`'s workspace reads it through the existing `ReadImageFileAsync` verified-read pipeline (hash-checked, same as the file viewer) rather than a raw path, and passes the bytes/media type to `IProviderAdapter.GenerateTextAsync` as an optional `TextGenerationSourceImage`. `OpenAiCompatibleProtocol.BuildChatCompletionRequestBody` switches the user message from a plain string to a `[{type:"text"},{type:"image_url", image_url:{url:"data:<mediaType>;base64,..."}}]` array when an image is supplied — the OpenAI vision content-part shape, supported by both adapters. The referenced file ID is persisted on `GenerationRecord`/`SavedGenerationSetting` (schema v14: `source_file_id`, `ON DELETE SET NULL` so a later permanent file deletion clears the reference rather than leaving it dangling) and carried through **Save settings** and **Use Again**. This is now "Source 1" of 3 fixed slots — see [Multi-source input slots](#multi-source-input-slots) below. Image-mode generation still accepts no source input at all.

## Multi-source input slots

`/generate` offers 3 fixed, generically-labeled source-image slots ("Source 1/2/3") for Text-mode generation, replacing the single source-image field with two more additive slots rather than a normalized/reorderable list. plan.md's aspirational per-model named input-slot roles (mask, reference image, first/last frame, source audio/video) don't apply here — this app has no per-model input-capability schema and no non-image source types those roles would validate against, so the 3 slots are functionally identical (each just becomes another ordered `image_url` vision content part) and reordering isn't meaningful (each slot is a fixed, independently-chosen dropdown, not an ordered general-source list).

Slots 2 and 3 are pure additions mirroring the original slot's exact mechanism, not a generalization of it: `GenerationDraft`/`SavedGenerationSetting`/`GenerationJobSnapshot` each gain `SecondarySourceFileId`/`TertiarySourceFileId` (schema v28: matching `secondary_source_file_id`/`tertiary_source_file_id` columns, added via plain `ALTER TABLE ADD COLUMN` — no table rebuild, since renaming a table to rebuild it was found this session to silently corrupt a dependent table's foreign-key reference via SQLite's auto-rewrite-on-rename behavior), and `GenerationRecord` additionally gains `SecondarySourceFileTombstone`/`TertiarySourceFileTombstone` (`FileIdentitySnapshot?`), mirroring its existing `SourceFileId`/`SourceFileTombstone` pair exactly. `DeleteFileRecordAsync`'s tombstone-writing `UPDATE generation_records SET tombstone_source_...WHERE source_file_id=$id` gained two structurally identical siblings keyed on the secondary/tertiary columns.

`LibraryRules.ValidateSourceFileIds` rejects the same file selected in more than one of the 3 slots (`LibraryValidationException`), called from every mutation path that accepts source IDs — not just the client-side check `Generate.razor`'s `HasDuplicateSourceSelection` uses to disable the submit button and show an inline error. `IProviderAdapter.GenerateTextAsync`/`OpenAiCompatibleProtocol.BuildChatCompletionRequestBody` gained matching `secondarySourceImage`/`tertiarySourceImage` parameters; the request body writes one ordered `image_url` part per non-null image after the text part, so a request with only slot 2 filled still gets exactly one image part. `GenerationHistoryDetail.razor` unifies what were two separate, non-adjacent single-source render blocks (a tombstone-or-nothing paragraph near the top, a live link in the actions row) into one list rendering all 3 slots in position order, each showing a live link, tombstone text, or nothing for an unused slot — closer to how the results list already interleaves live and tombstoned entries.

## Typed generation settings

`GenerationSettings` (`Domain/LibraryModels.cs`) is a record of 5 independently nullable fields — `Temperature`, `TopP`, `MaxTokens`, `FrequencyPenalty`, `PresencePenalty` — the standard OpenAI chat-completion parameters. A null field means **Use Provider Default**: it is omitted entirely from the outbound JSON request body rather than replaced with a guessed value. Setting a field makes it explicit; clearing it back to blank in the UI is **Reset to Provider Default**. This is scoped to Text-mode models only — both current `ProviderType`s (`OpenAi`, `GenericOpenAiCompatible`) share `OpenAiCompatibleProtocol.BuildChatCompletionRequestBody`, and these 5 parameters belong to the `chat/completions` shape; the OpenAI-compatible `images/generations` endpoint has no equivalent, so Image-mode has no settings schema at all.

Because both provider types are OpenAI-shaped, the schema is fixed and identical for every Text-mode model rather than a per-model-configured concept — unlike plan.md's aspirational per-model/per-modality maintained schemas sourced from provider adapters and supplemented by model-discovery metadata. There is nothing to attach to `Model`/`ModelEdit.razor`, and no new **Needs Review** trigger is needed: the schema never changes independently of a code update, so [Model Needs Review propagation](#model-needs-review-propagation)'s existing triggers (provider model ID/mode change) remain the complete set. A manual/advanced-JSON settings editor for models "without a maintained schema" is also not needed today, since every current provider type always has this one.

`LibraryRules.ValidateGenerationSettings` enforces OpenAI's documented ranges (temperature 0–2, top_p 0–1, max_tokens ≥ 1, frequency/presence penalty −2–2) from every `SqliteLibraryDatabase` mutation path that accepts settings, mirroring `NormalizeConnectionTimeoutSeconds`'s existing pattern — not just client-side Razor validation, so an out-of-range value can never reach persistence or the outbound request regardless of caller.

The 5 fields flow as a unit alongside Prompt/ResultCount/SystemInstructions through `GenerateForm`, `GenerationDraft`, `SavedGenerationSetting`, `GenerationRecord` and `GenerationJobSnapshot` (schema v27: 5 new nullable columns each on `generation_records`, `saved_generation_settings` and `generation_drafts`) — draft autosave, **Save**/**Save As**, loading a saved setting, and **Use Again** from history all carry them the same way the prompt already does, and a generation's exact settings are preserved in its history record rather than only reflecting whatever the schema happens to produce later. `Generate.razor` renders the 5 fields as plain nullable `InputNumber`s inside a collapsed **Generation settings** `<details>` section next to the source-image field (the same "leave blank to use the default" convention `ConnectionEdit.razor`'s connection-timeout override already established, reused rather than inventing a separate labelled Reset control), gated to Text mode the same way that field already is. Following [Saved-setting revision conflicts](#saved-setting-revision-conflicts)' `SourceFileId` precedent, a settings value is never physically cleared from the in-memory form on a mode switch — only gated at the point of save/request — so switching back to a Text-mode model doesn't lose what the user typed. `BuildConflictDiffRows()` gained a row per setting alongside the existing model/prompt/source-file rows.

`OpenAiCompatibleProtocol.BuildChatCompletionRequestBody` writes each of the 5 JSON keys (`temperature`, `top_p`, `max_tokens`, `frequency_penalty`, `presence_penalty`) only when its corresponding field is non-null; `IProviderAdapter.GenerateTextAsync` and both adapters thread the settings through as a new optional parameter. `GenerateImageAsync`/`BuildImageGenerationRequestBody` are untouched. `ImprovePromptAsync`'s direct adapter call intentionally passes no settings — prompt improvement stays out of scope.

## Cancellation

`/generate`'s **Generate** action enqueues a job with `GenerationQueueService` (see [Generation queue and concurrency](#generation-queue-and-concurrency)), which creates the `CancellationTokenSource` passed to the adapter call, the result commit and the history insert once the job starts running. Clicking **Cancel** (shown while a job is queued or running for the active tab) requests cancellation; a still-queued job is removed before it ever runs, and a running one unwinds before `RecordTextGenerationResultAsync`/`RecordImageGenerationResultAsync` executes — either way no `GenerationRecord` is created at all, and the tab shows a message that the provider may still process or charge for an already-sent request rather than guessing a terminal status. This deliberately does not implement the documented `Submission Outcome Unknown` state, per-stage cancellation semantics (before-submission vs. mid-upload vs. already-accepted), or reconciliation.

## Generation history filters

`/generation-history` filters its already-loaded list client-side by status, mode, model label and provider (each an independent `<select>` bound to a plain string field, `""` meaning no filter) plus an inclusive from/to date range (`<input type="date">` bound directly to nullable `DateOnly?` fields, compared against `record.CreatedAt.ToLocalTime()` converted to a `DateOnly`) via a computed `FilteredRecords` property, plus a **Clear filters** action that resets all of them. There is no server-side query, and no persistence of the filter selection across navigation.

## Connection credential and verification status

`Connections.razor`'s `StatusLabel` checks `Connection.CredentialRequiresRepair` first (highest precedence — **Credential State Requires Repair**), then `HasCredential`, so a connection with no stored API key shows **Credentials Required** rather than **Unverified**/**Test Failed**, even if it happens to carry a stale successful `LastTestStatus` from before a credential was removed. `/generate` mirrors this through a computed `CredentialBlocked(Connection)` helper (`!HasCredential || CredentialRequiresRepair`): a blocked connection disables the **Generate** submit button and shows a blocking notice (the repair banner when repair is needed, otherwise the credentials-required message) linking to `/connections/{id}`, while `SelectedConnection.IsUnverified` (any status other than `Success`, checked only when not blocked) shows a non-blocking warning instead; `GenerateAsync`, `ImprovePromptAsync`, and `GenerationQueueService.ExecuteAsync` all re-check the same condition server-side (in-process) before calling the adapter, since the UI guard alone is not authoritative. `SqliteLibraryDatabase.UpdateConnectionAsync` already unconditionally resets `LastTestStatus` to `Untested` on every edit, so retesting-after-edit is already enforced; what remains open is a **Secure Storage Unavailable** state (credential store itself failing versus the credential being absent), an **Authentication Failed** state derived from inspecting a connection-wide `401` rather than a generic failed test, and collapsing the unverified warning into a one-time per-revision confirmation instead of showing it on every use.

## Revisioned credential lifecycle

Schema v23 replaces "overwrite the stored key on Save" with a candidate/promote sequence backed by a non-secret ledger, per plan.md's revisioned credential lifecycle (excluding the remote-job/cleanup-tied **Submission Outcome Unknown** portions — no such infrastructure exists in this app). `connections` gains `credential_revision_id`/`credential_requires_repair`; a new `connection_credential_revisions` table (`connection_id, revision_id, purpose` where purpose is `Candidate`/`Active`, `created_at`) tracks which revision-suffixed secure-storage entries exist, since MAUI's `SecureStorage` has no key-enumeration API — only get/set/remove by exact key name.

`ILibraryWorkspace` exposes `BeginCredentialCandidateAsync` (mints a revision ID, inserts a `Candidate` row), `PromoteCredentialRevisionAsync` (one transaction: flips the row to `Active`, updates the connection's pointer/`HasCredential`/clears `CredentialRequiresRepair`, deletes every other row for that connection, returns `SupersededRevisionIds`), `DiscardCredentialCandidateAsync`, `MarkCredentialRequiresRepairAsync` (only ever sets the flag — never touches the pointer or deletes anything), `GetCredentialLedgerSnapshotAsync`, and `DeleteCredentialLedgerRowAsync`. `PromoteCredentialRevisionAsync` deliberately never touches `LastTestStatus`/`LastTestedAt`/`LastTestMessage`; the caller records the test outcome separately via the existing `SetConnectionTestResultAsync`, which keeps promotion's DB-transaction shape simple and means a silently-adopted legacy credential's prior test status is preserved automatically rather than needing a special-cased "don't reset" parameter.

`ISecureCredentialStore` (Gui-layer, since `Infrastructure` cannot reference `SecureStorage`) is revision-aware: `GetActiveAsync`/`SetActiveAsync`/`RemoveActiveAsync` and `GetCandidateAsync`/`SetCandidateAsync`/`RemoveCandidateAsync` take a revision ID; `GetLegacyAsync`/`RemoveLegacyAsync` address the pre-revision key every existing connection used before this feature shipped. `MauiSecureCredentialStore` keys candidates under a genuinely separate secure-storage prefix (`connection-candidate:...`) from active entries (`connection:...:{revisionId}`), per plan.md's "separate indexed secure-storage namespace".

`ConnectionEdit.razor`'s Save, when a new key was typed: persists non-credential fields first (as before), then stages the value as a candidate, runs a fresh `TestConnectionAsync` against the exact staged value (never trusting an earlier **Test Connection** click, since the field could have changed since), and on success writes the candidate into the active secure-storage slot, reads it back to verify the write, and only then calls `PromoteCredentialRevisionAsync` before deleting the candidate and any superseded active secure-storage keys (best-effort — a deletion failure here is not fatal; reconciliation's superseded-active sweep catches it next time). On test failure, Save does not navigate away; it shows a decision panel (**Keep Existing Key** discards the candidate, **Save New Key as Unverified** promotes it anyway after an explicit warning) instead of silently discarding the typed key or silently saving an unverified one. A `CredentialRequiresRepair` connection skips the masked "Credential stored" view entirely and shows the key input directly behind an error-styled banner.

`CredentialReconciliationService` (Gui/Services singleton, same shape as `ManagedContentWatchService`/`GenerationQueueService`: `Start()` subscribes to `AppLibraryState.Changed`, called from `MainLayout.razor`) re-sweeps every time a workspace opens or switches. For each connection's ledger snapshot: every `Candidate` row found is orphaned by definition (there is no cross-restart in-progress-edit concept) and is deleted along with its candidate secure-storage key; a `HasCredential` connection with no committed pointer and no ledger revisions at all is a pre-existing connection from before this feature — its legacy key is read, promoted into revision 1, and removed, with no forced retest and no visible change (confirmed with the user: silent one-time adoption), or flagged **Requires Repair** if the legacy key is somehow already gone; a committed pointer with no matching/readable active revision is flagged **Requires Repair** without touching anything else; and any other `Active` row under a connection with a valid, readable committed pointer is a leftover from a crash between the promotion transaction and its post-commit secure-storage cleanup, cleaned up here.

Verified by `CredentialRevisionLifecycleTests.cs` (ledger CRUD, promotion/supersession, cascade-on-permanent-delete), `CredentialReconciliationServiceTests.cs` (orphaned-candidate sweep, repair detection via both a missing ledger row and a missing secure-storage value, stray-superseded-row cleanup, legacy adoption preserving test status, repair-when-legacy-key-is-gone), and `OpeningVersionTwentyTwoLibraryAddsCredentialRevisionLedger` (schema migration).

## Connection timeout override

`Connection.TimeoutSeconds` (schema v16, nullable) is validated by `LibraryRules.NormalizeConnectionTimeoutSeconds` against a shared 5–600 second range (`MinimumConnectionTimeoutSeconds`/`MaximumConnectionTimeoutSeconds`); `null` means the application default, `LibraryRules.DefaultConnectionTimeoutSeconds` (100 seconds — chosen to match `HttpClient`'s prior default so unconfigured connections behave exactly as before). `ConnectionEdit.razor` exposes it as an `InputNumber` under **Advanced connection settings** and threads the candidate value into the probe `Connection` built for **Test Connection**, so a not-yet-saved timeout value is exercised before the user commits it.

All four `IProviderAdapter` HTTP calls (`TestConnectionAsync` delegates to `ListModelsAsync`) now go through `OpenAiCompatibleProtocol.SendAsync(httpClient, request, connection, cancellationToken)`, which creates a `CancellationTokenSource` for `connection.TimeoutSeconds ?? DefaultConnectionTimeoutSeconds` seconds, links it with the caller's `cancellationToken`, and sends/reads the response on the linked token. A `catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested && !cancellationToken.IsCancellationRequested)` clause converts a timeout specifically into `ProviderAdapterException($"The request timed out after {timeoutSeconds} seconds.")`, while a real caller-driven cancellation (the external token itself cancelled) still propagates as `OperationCanceledException`/`TaskCanceledException` unchanged. This closes a latent bug: previously each adapter method called `_httpClient.SendAsync` directly against the shared typed `HttpClient`'s own (default ~100s) `Timeout`, which throws a bare `TaskCanceledException` indistinguishable from user cancellation — on `/generate`, `GenerateAsync`'s `catch (OperationCanceledException)` block would have reported a slow provider as "Generation cancelled by the user" instead of a provider timeout. `DependencyInjection.AddSlopFactoryInfrastructure` now sets each adapter's injected `HttpClient.Timeout` to `Timeout.InfiniteTimeSpan` so `SendAsync`'s linked-token logic is the only timeout enforcement in play. Both adapters' `TestConnectionAsync` methods dropped their now-dead `catch (TaskCanceledException) when (!cancellationToken.IsCancellationRequested)` clause, since a timeout now always surfaces as `ProviderAdapterException`, already handled by an existing catch clause there.

## Additional connection headers

`Connection.AdditionalHeaders` (schema v17, `connection_headers` child table keyed by `(connection_id, name)`) holds plain `ConnectionHeader(Name, Value)` pairs for gateway/routing use cases (an organization header, a routing key, an API version pin) — explicitly non-secret by construction. `LibraryRules.NormalizeConnectionHeaders(headers, credentialHeaderName)` caps the list at 10 entries and 500 characters per value, rejects duplicate names (case-insensitive), and refuses both standard transport/hop-by-hop headers (`Host`, `Content-Length`, `Connection`, `Transfer-Encoding`, etc.) and anything that would otherwise carry a credential (`Authorization`, `Proxy-Authorization`, `Cookie`/`Set-Cookie`, or the connection's own configured credential header name) — those are refused outright rather than accepted and stored as plaintext, since secret-header handling would need the same secure-storage-backed candidate/promotion machinery as the primary API key, which does not exist. `SqliteLibraryDatabase.ReplaceConnectionHeadersAsync` deletes and reinserts the full set inside the same transaction as the connection row update, so header changes are atomic with everything else `CreateConnectionAsync`/`UpdateConnectionAsync` writes; `GetConnectionAsync`/`ListConnectionsAsync` load headers via a second query per connection immediately after the row read (SQLite/`Microsoft.Data.Sqlite` has no MARS, so a second reader on the same connection cannot be open concurrently with the first). `ConnectionEdit.razor` renders/parses them as a `Name: Value`-per-line textarea (`FormatHeaderLines`/`ParseHeaderLines`), reusing the same `LibraryRules.NormalizeConnectionHeaders` validation for both the **Test Connection** probe and **Save**. `OpenAiCompatibleProtocol.ApplyAdditionalHeaders` applies them via `TryAddWithoutValidation` on every adapter request, right after `ApplyAuthorization`.

## Generation-history detail page

`/generation-history` no longer shows a generation record's full prompt/system-instructions/error/usage/result-links inline in the list; that content moved to a new `GenerationHistoryDetail.razor` at `/generation-history/{Id}`, which fetches the single record via the existing `GetGenerationRecordAsync` (already used by `Generate.razor`'s **Use Again** route, so no new workspace method was needed) and renders exactly what the list row used to render. Each list row is now just the summary line plus **View Details** (new, links to the detail page) and **Use Again** actions. The prompt-improvement history section at the bottom of `/generation-history` is untouched — it stays inline because a `PromptImprovementRecord` is a much smaller shape (no source file, no separate settings) where a dedicated detail page would add navigation friction without showing meaningfully more than the existing inline `<details>` disclosure for its candidates already does.

## Improvement-candidate size bound

`CreatePromptImprovementRecordAsync` validates every entry in `candidates` against `LibraryRules.ValidateGenerationTextLength` (the same 1 MiB bound as the raw prompt and guidance) before writing the attempt. If a provider ever returned an oversized candidate, the attempt fails to persist and `Generate.razor`'s `ImprovePromptAsync` (which wraps the persistence call in its own `catch (SlopFactoryException)`) degrades gracefully: the candidates the user already sees on screen (`_improvementCandidates`, assigned before persistence is attempted) are unaffected, but `_lastImprovementRecordId` stays `null`, so accepting one of those candidates and generating from it will not link back to any prompt-improvement record. This is a deliberate, narrow trade-off for an edge case that should not occur with any normally-behaving provider.

## Partially Completed generation status

`GenerationStatus` gained a third value, `PartiallyCompleted`, requiring no schema change since `generation_records.status`/`prompt_improvement_records.status` were always plain `INTEGER` columns with no `CHECK` constraint restricting their values. `LibraryWorkspace.DetermineGenerationStatus(committedCount, requestedCount)` is the single shared decision point used by both `RecordTextGenerationResultCoreAsync` and `RecordImageGenerationResultCoreAsync`: zero committed results is `Failed` (unchanged), all requested results committed is `Completed` (unchanged), and anything in between — a provider returning fewer candidates than the request's `resultCount` without the adapter call throwing — is now `PartiallyCompleted` rather than silently reading as a full `Completed`. `Generate.razor`'s `GenerationStatusLabel` and `GenerationHistory.razor`'s `StatusLabel` both switch on the new value, and both pages show an additional "N of M requested results were committed" line specifically for that status. This does not add **per-child** status — an individual candidate within one multi-result request still has no independent identity, retry, or status; the whole request remains one atomic database write — and does not add transport-archive extraction, since no provider adapter currently documents or produces an archive-packaged multi-result response.

## Provider content-filter detection (safety-blocked results)

Provider Safety Responses' full spec (concealment/reveal session state, per-file persistent override
preferences, external-open re-authorization, cross-duplicate shared classification events, and
**Provider Blocked After Delivery** late reclassification) all require either an async-job/polling
adapter (already deferred) or a "permitted but flagged, delivered anyway" signal that the plain OpenAI
chat-completions and images/generations APIs simply don't have — `finish_reason` is only ever
`stop`/`length`/`content_filter`/`tool_calls`/`function_call`, and images/generations has no per-image
content-filter field at all. The one part of the spec that maps to something real: a chat-completion
choice can come back with `finish_reason: "content_filter"` and empty content when OpenAI's own
moderation blocks that specific candidate, and previously `ParseChatCompletionResult` silently dropped
it — the choice just contributed to a smaller `Texts` list with no record of why, which existing
`PartiallyCompleted`/`Failed` status logic already tolerated as an ordinary shortfall but with no
sanitized explanation available anywhere.

`ParseChatCompletionResult` now checks each choice's `finish_reason` first: a `"content_filter"` choice
is counted into a new `safetyBlockedCount` instead of attempting to read its (empty) `content`, and
`TextGenerationResult` gained a `SafetyBlockedCount` field (default `0`, so every existing call site
across the fake-adapter test suite compiles unchanged). If every choice is blocked, `Texts` is empty
but the method no longer throws `ProviderAdapterException("no usable text results")` — that guard now
only fires when *both* `Texts` is empty and `SafetyBlockedCount` is zero, since an all-blocked response
is meaningfully different from a malformed one. `GenerationRecord` gained a matching
`SafetyBlockedCount` column (schema v29, `generation_records.safety_blocked_count INTEGER NOT NULL
DEFAULT 0`), threaded through `GenerationQueueService.ExecuteAsync` →
`RecordTextGenerationResultAsync`/`RecordTextGenerationResultCoreAsync` →
`SqliteLibraryDatabase.CreateGenerationRecordAsync` unchanged in shape otherwise — image-mode
generation always passes `0`, since no equivalent provider signal exists for it. `Generate.razor`'s
run cards and `GenerationHistoryDetail.razor` both show a new "N result(s) were blocked by the
provider's content safety system and were not saved" note whenever `SafetyBlockedCount > 0`, alongside
(not instead of) the existing partial-completion detail line, since both can be true of the same
record (some choices filtered, some others also simply missing).

## Generation text length bound

`LibraryRules.ValidateGenerationTextLength(value, fieldName)` (1 MiB, `MaximumGenerationTextUtf8Bytes`) closes a gap that existed since the very first generation slice: nothing previously validated the length of a prompt, system-instructions value, or prompt-improvement raw-prompt/guidance before persisting it, even though `Generate.razor`'s textareas already declared `maxlength="1048576"` as a client-side backstop matching this exact bound. It is called from `SqliteLibraryDatabase.CreateGenerationRecordAsync` (prompt, system instructions), `CreateSavedSettingAsync`/`UpdateSavedSettingAsync` (prompt, system instructions), and `CreatePromptImprovementRecordAsync` (raw prompt, guidance) — the domain layer, not the GUI, so the bound holds regardless of caller. An "improved prompt" the user accepts becomes the ordinary `Prompt` field once accepted, so it is covered by the same check rather than needing a separate one. There is no CRLF/CR normalization and no interactive atomic oversized-edit rejection (the GUI's `maxlength` attribute is the only thing preventing an over-length edit in the browser; a bypass would surface as a save-time `LibraryValidationException`, not a live prevented keystroke).

## Bounded automatic retry for model listing

`OpenAiCompatibleProtocol.SendAsync` gained an `allowRetry` parameter (default `false`). When `true` and the response status is `429 Too Many Requests`, it retries the request up to `MaxRetryAttempts` (3) times before returning the failed result to the caller, computing each delay via `ComputeRetryDelay`: honor the response's `Retry-After` header (delta-seconds or HTTP-date form) if present, clamped to `MaxRetryDelay` (30 seconds, an application-chosen safety bound — nothing in a provider's documented contract obligates it to respect that cap, so this exists purely so a provider-supplied `Retry-After` can never stall the app indefinitely); otherwise `2^attempt` seconds plus 0–500ms of jitter, clamped the same way. Retries happen inside the *same* linked timeout token as the initial attempt — the connection's configured timeout is a ceiling on the whole operation, not reset per retry — and each retry re-sends a **cloned** `HttpRequestMessage` (`CloneRequestAsync`, copying method/URI/headers/content) since a `HttpRequestMessage` cannot be sent twice.

Only both adapters' `ListModelsAsync` methods pass `allowRetry: true`; `TestConnectionAsync` inherits this transparently since it just calls `ListModelsAsync`. `GenerateTextAsync`/`GenerateImageAsync` do not set it, leaving them at the pre-existing single-attempt behavior — this split enforces the plan's documented distinction verbatim: model listing is idempotent and provider-safe to retry blind, while a generation-submission request is only safe to retry automatically with a provider-confirmed idempotency key, which this application does not implement, so it must never auto-retry silently. `ProviderAdapterTests` proves both halves of this: a `ListModelsAsync` call that returns `429` once then `200` succeeds transparently after one retry, a `ListModelsAsync` call that always returns `429` gives up after a small bounded number of attempts and still reports the existing rate-limiting message, and a `GenerateTextAsync` call that always returns `429` invokes the fake handler exactly once — proving no automatic retry ever happens there. Tests force `Retry-After: 0` on their fake `429` responses so the bounded-backoff path resolves near-instantly rather than actually sleeping through exponential delays.

## Per-model text result format

`Model.TextFormat` (schema v21, `TextResultFormat.Markdown`/`PlainText`, defaulting to `Markdown`) controls the extension and media type `LibraryWorkspace.RecordTextGenerationResultCoreAsync` uses when committing each returned text candidate — `(".md", "text/markdown")` or `(".txt", "text/plain")`, computed once from the resolved `model.TextFormat` and reused for every candidate's staging filename, managed filename and `FileRecord.MediaType`. `GenerationRecord.TextFormat` (`generation_records.text_format`, nullable — `null` for image generations) snapshots which format the request used, threaded through `CreateGenerationRecordAsync`'s new trailing parameter; `ModelEdit.razor` exposes the choice as a `<InputSelect>` shown only when `_form.Mode == GenerationMode.Text`. There is no `.json` structured-output format, since that requires provider-adapter support for requesting and validating structured JSON output that does not exist, and no streaming incremental display — both remain open per `milestone2.md`.

## Model Needs Review propagation

`Model.NeedsReview`/`SavedGenerationSetting.NeedsReview` (schema v20) let `SqliteLibraryDatabase.UpdateModelAsync` flag a model and its dependents when a configuration change could invalidate assumptions saved settings made about it. The comparison is against the *stored* values fetched at the start of the call (`existing.ProviderModelId`/`existing.Mode`), not the in-memory form state, so the check is authoritative regardless of what the caller believes changed; a match on label-only or `SupportsSystemInstructions`-only edits leaves `NeedsReview` untouched. When the flag transitions from `false` to `true`, the same transaction also sets `needs_review=1` on every `saved_generation_settings` row with `model_id=$id AND state=0` (recycled saved settings are left alone, matching the "active dependents" scope used by the model/connection cascade rules elsewhere). `MarkModelReviewedAsync` is the inverse — it is a deliberate stand-in for the "until its configuration validates" language in the product spec, since there is no real capability/settings-schema re-verification to run yet; it simply clears both flags.

`ModelEdit.razor` mirrors the transition check client-side (`_originalProviderModelId`/`_originalMode` captured in `OnInitializedAsync`) purely so it can show the confirmation panel *before* calling `UpdateModelAsync` — the actual decision of whether to set the flag is still made server-side from stored values, so the two checks are independent and the client-side one is only a UX gate, not a security or correctness boundary. `/generate` excludes any model with `NeedsReview` from `_models` (computed once in `OnInitializedAsync` alongside a `_hasNeedsReviewModels` flag used only to pick the right empty-state message), which is the mechanism enforcing "cannot be used for generation until validated." A saved setting whose model became unselectable this way is not specially handled — it falls into the pre-existing "model unavailable" branch that already covers a recycled or deleted model reference, so no new fallback logic was needed there.

## Prompt-improvement history

`PromptImprovementRecord` (schema v19, `prompt_improvement_records`, candidates stored as a JSON array string via `System.Text.Json`) is a distinct, lightweight AI-operation entry — never associated with library files — created by `ILibraryWorkspace.RecordPromptImprovementAttemptAsync` on *every* submitted `/generate` **Improve Prompt** attempt, success or failure, mirroring the `CreateGenerationRecordAsync` snapshot pattern (`model_id` nullable with `ON DELETE SET NULL`, plus a frozen `model_label`/`provider_model_id`/`provider_type` snapshot so the record stays meaningful after the model is gone). `Generate.razor`'s `ImprovePromptAsync` now always records an attempt in its `finally` block — after either the try succeeds (populating `candidates`/token usage) or the catch captures `attemptError` — so a failed or retried attempt never overwrites a prior one; each click is its own row. `UseImprovedPrompt` remembers `_lastImprovementRecordId` as `_acceptedImprovementRecordId`, which `GenerateAsync` then passes as `promptImprovementRecordId` into `RecordTextGenerationResultAsync`/`RecordImageGenerationResultAsync`, populating the new nullable `GenerationRecord.PromptImprovementRecordId` (`generation_records.prompt_improvement_record_id`, `ON DELETE SET NULL` against `prompt_improvement_records`). The link is not cleared if the prompt is edited further after acceptance — it simply tracks the most recently accepted attempt, a deliberate simplification over precisely tracking "is the submitted prompt still exactly the accepted candidate."

`/generation-history` shows prompt-improvement records in their own **Prompt improvement history** panel (`GetPromptImprovementHistoryAsync`, newest first) rather than merged into the primary filtered `GenerationRecord` list — a real scope reduction from the documented unified operation-type display, since the existing status/mode/model filters are typed against `GenerationRecord` and would need generalizing to cover a second record shape. A generation record that used an accepted suggestion shows a **Prompt improvement was used** note via `record.PromptImprovementRecordId is not null`.

## Connection provider-type change

A connection's provider type can only change when it has zero *active* dependent models. `ILibraryWorkspace.ChangeConnectionProviderTypeAsync` is intentionally a separate method from `UpdateConnectionAsync` — inserting a `providerType` parameter into the existing signature would have meant a positional-argument break across every call site, whereas a dedicated method needed no changes to `CreateConnectionAsync`/`UpdateConnectionAsync` at all. It validates the connection is active, counts `models WHERE connection_id=$id AND state=0` and throws `LibraryValidationException` if that count is non-zero, then resets `GenericModalitySettings` to `GenericConnectionModalitySettings.Default` (since generic per-modality settings are meaningless once the provider type is no longer `GenericOpenAiCompatible`, and stale settings should not silently persist into a future switch back) and resets the test status to `Untested` like every other connection edit. `ConnectionEdit.razor` computes `_hasDependentModels` once in `OnInitializedAsync` (`GetActiveModelsAsync().Any(model => model.ConnectionId == Id)`) and disables the provider-type `<InputSelect>` only when true; on save, if the selected provider type differs from `_originalProviderType`, it calls `ChangeConnectionProviderTypeAsync` after the main `CreateConnectionAsync`/`UpdateConnectionAsync` call so the reset-to-default modality settings are the final write, regardless of whatever stale values remained in the (now-hidden) per-modality form fields.

Connection-label-change independence from dependent models required no code change: `Model` stores only `ConnectionId`, never a cached copy of the connection's label, so every page resolves the current label by looking up the connection fresh each render. This is exercised by the existing `UpdatingAConnectionResetsItsTestStatusWithoutAffectingDependentModels` test.

## Generic connection per-modality settings

`Connection.GenericModalitySettings` (schema v18, six columns on `connections`: an enabled flag and an optional relative-path override for each of models/text-generation/image-generation) is meaningful only for `ProviderType.GenericOpenAiCompatible` — `OpenAiProviderAdapter` never reads it, since the dedicated OpenAI adapter always uses fixed, documented paths. `LibraryRules.NormalizeGenericModalitySettings` defaults a `null` settings value to `GenericConnectionModalitySettings.Default` (all three modalities enabled, no path overrides) and validates each configured path through `NormalizeRelativePathOverride`, which rejects an absolute URL or a `..` segment; a structural scheme/host takeover is impossible regardless, because `OpenAiCompatibleProtocol.CombineUrl` builds the final URL by string-concatenating the override onto the connection's own base URL rather than parsing it as an independent URI. `GenericOpenAiCompatibleProviderAdapter`'s three HTTP-calling methods each read `connection.GenericModalitySettings?.<Path>Override ?? "<default-path>"` and check the corresponding `...Enabled` flag first, throwing `ProviderAdapterException` before constructing any `HttpRequestMessage` when a modality is disabled. `ConnectionEdit.razor` renders the three enabled/path-override rows only when `_form.ProviderType == ProviderType.GenericOpenAiCompatible`, alongside a computed (client-side string-concatenation, not a live network probe) resolved-endpoint preview per modality.

## Model catalogue caching

Each connection persists its latest discovered-model catalogue (schema v15: `connections.catalogue_retrieved_at`/`catalogue_possibly_stale` plus a `connection_model_catalogue` table of `(connection_id, provider_model_id, display_label)`, replaced wholesale on every refresh). `ILibraryWorkspace.GetModelCatalogueAsync` reads it; `RefreshModelCatalogueAsync` replaces the cached entries and sets the retrieval timestamp while clearing the possibly-stale flag; `MarkModelCatalogueRefreshFailedAsync` sets the possibly-stale flag without touching the retained entries or timestamp. `ModelEdit.razor`'s **Load Models** action calls the adapter directly for its own discovery dropdown (`_discoveredModels`, unchanged) and separately persists the same result into the cache — a successful call refreshes it, a failed one marks it possibly stale — then displays the cache's retrieval timestamp/age plus a **Possibly Stale** (immediate, from a failed refresh) or **Stale** (`DateTimeOffset.UtcNow - RetrievedAt > LibraryRules.ModelCatalogueStalenessPeriod`, 7 days) label. `Models.razor` loads each distinct connection's catalogue once per page load and marks a configured model **Not Currently Listed** when its `ProviderModelId` is absent from that connection's cached entries and a catalogue has actually been retrieved (`RetrievedAt is not null`) — a connection with no catalogue yet renders no judgment either way. None of this ever triggers a network request, deletes, or disables a configured model; it is a passive label only. The catalogue is refreshed solely through the explicit **Load Models** action — not automatically during initial connection setup or connection retesting — and there is no per-adapter override of the 7-day staleness period.

## Per-model system-instructions capability

`Model.SupportsSystemInstructions` (set in `ModelEdit.razor`, persisted by `SqliteLibraryDatabase.CreateModelAsync`/`UpdateModelAsync`) now gates behavior on `/generate` rather than existing only as a stored flag. A computed `SelectedModel` property replaces the model lookup previously duplicated across `SelectedModelMode`, and the System Instructions field renders only when `SelectedModel?.SupportsSystemInstructions == true` for a Text-mode model — otherwise a note explains why the field is absent. `GenerateAsync` and `SaveSettingsAsync` both check `model.SupportsSystemInstructions`/`SelectedModel?.SupportsSystemInstructions` directly before including `_form.SystemInstructions`, so switching from a capable model to an incapable one and generating without revisiting the (now-hidden) field cannot leak a stale value into the request or a saved setting. The generic adapter still does not inspect provider responses for signs a `system` role was rejected, so there is no confirmation flow that offers to flip the flag automatically after a provider-side rejection.

## Prompt improvement

`/generate` offers an **Improve Prompt** panel, shown whenever at least one active Text-mode model exists. The user picks an improvement model (any active Text-mode model, independent of the output model) and may supply free-text guidance; `ImprovePromptAsync` calls `IProviderAdapter.GenerateTextAsync` against the improvement model, passing the current prompt as the user message and a fixed, versioned instruction string (`PromptImprovementTemplate`, formatted with the output model's mode) through the existing `system`-instructions parameter rather than inventing a second channel. The returned `TextGenerationResult.Texts` are shown as candidates the user can individually accept into the prompt textarea (`UseImprovedPrompt`) or ignore; nothing is written until a candidate is chosen. This is a purely in-session helper — there is no raw-vs-improved persistence on `GenerationRecord`/`SavedGenerationSetting`, no **Include Target Model Identity**/**Include System Instructions in Improvement**/**Include Compatible Sources** opt-ins, no **View Instruction** display, and no candidate size bounds or **Refused**/**Unsupported Response**/**Interrupted**/**Needs Review** handling.

## Generation drafts and tabs

`GenerationDraft` (schema v22: `generation_drafts`) replaces `/generate`'s single page-level form with a per-library set of persisted draft tabs, reached through `ILibraryWorkspace.GetDraftsAsync`/`GetDraftAsync`/`CreateDraftAsync`/`ReplaceDraftStateAsync`/`DuplicateDraftAsync`/`DeleteDraftAsync`/`ReorderDraftsAsync`. A draft snapshots exactly the fields the generation form itself edits (model, prompt, system instructions, source image, result count, destination folder, plus the prompt-improvement model/guidance) and a nullable `CustomTitle` — `null` is the "automatic title" sentinel rather than a separate flag, so resetting a rename is just `ReplaceDraftStateAsync(..., customTitle: null, ...)`. There is a single whole-state-replace method backing both autosave and manual rename/reset, and `ReorderDraftsAsync` follows the same whole-state-replace philosophy rather than a granular move-by-index method: it takes the complete ordered list of draft IDs, validates it against the current set (throwing `LibraryValidationException` on a mismatched count or set), and rewrites every `tab_order` value inside one transaction. `model_id`/`source_file_id`/`improvement_model_id` are nullable with `ON DELETE SET NULL`, matching `SavedGenerationSetting`'s pattern — a later-recycled-and-deleted model or file just clears the reference rather than blocking.

Unlike every other entity in this application, `GenerationDraft` has **no `LibraryRecordState`/recycle columns at all** — closing a tab is an instant, permanent `DeleteDraftAsync` with no recycle-bin entry and no undo. This is a deliberate, narrow exception to the app's usual safety net: a draft is working form state rather than generated content, and **Save settings** already exists as a standing way to keep one before closing, so adding a second recovery path for the same concern was judged not worth the schema/UI complexity.

`Generate.razor` renders a plain-HTML tab strip (no new component library) above the existing form; `_form` is repopulated from the active draft on every switch, and `GenerateForm.Title` is gone entirely — naming a *tab* (`_tabTitleInput`, mapped to `CustomTitle`) and naming a *saved setting* (`_settingsTitle`, used only by **Save settings**) are independent, decoupled concerns now. Switching tabs flushes any pending debounced autosave for the outgoing draft synchronously before loading the new one, so an edit is never silently lost on switch; `_lastResult`/`_loadedSettingsId`/`_loadedTitle`/the in-memory prompt-improvement candidates all reset on switch rather than living on `GenerationDraft`, a deliberate simplification matching this app's fully-synchronous generation model (switching away from a tab mid-generation loses visibility of that generation's progress/result, though the close button for that specific draft stays disabled via a tracked `_busyDraftId` so it cannot be discarded out from under an in-flight request). `/generate/{SettingsId}` and `/generate/history/{HistoryId}` now create a **new** draft tab alongside whatever is already open (tracked via `_consumedSettingsId`/`_consumedHistoryId` so revisiting the same route on an already-mounted page does not spawn a duplicate tab) rather than replacing the page's only form state, reusing the same saved-setting/history snapshot and `SavedSettingsModelUnavailable` fallback logic as before.

Autosave is a page-level cancel-and-restart `Task.Delay(800ms)` plus `CancellationTokenSource`, calling `ReplaceDraftStateAsync` and driving a `Saving`/`Saved`/`Not Saved` status shown near the tab strip, with a **Retry Save** action on failure — pure client-side Razor/C#, identical on Windows and Android, no platform-conditional code or `SignalR`/`Timer` machinery. Each tab also has **‹**/**›** move buttons (disabled at the respective end of the strip) that swap the dragged draft's ID with its neighbor in a locally computed ordered-ID list and pass the whole list to `ReorderDraftsAsync`; this was chosen over drag-and-drop specifically because it needs no pointer-drag JS interop and activates identically via mouse, touch, and keyboard.

Two gates flush a pending debounced autosave instead of silently losing it. First, `Generate.razor` implements `IAsyncDisposable` rather than `IDisposable`, so Blazor awaits `DisposeAsync` (which calls the same `FlushPendingAutosaveAsync` already used for in-page tab switches) when the user navigates away from `/generate` entirely — previously `Dispose()` only cancelled the pending timer, discarding whatever was typed in the last ~800 ms. Second, `AppLibraryState` exposes a `Closing` event (`event Func<Task>?`, its invocation list awaited in registration order) raised immediately before `SwitchAsync`/`RelinkAsync`/`AdoptCopyAsync`/`CloseInvalidLibraryAsync` replace or null out `Workspace` — while the outgoing workspace is still valid, so a flush against it can actually succeed before it's disposed; `Generate.razor` subscribes to it in `OnInitializedAsync`. `Closing` is deliberately *not* raised ahead of `CloseUnavailableLibraryAsync`, since that path only runs once the workspace's storage is already confirmed unreachable, where a flush attempt could only add a doomed I/O wait. True OS-driven application-exit is out of reach of this mechanism: MAUI's `Window.Destroying` is a plain synchronous event with no cross-platform way to defer process exit for async cleanup, and Android can kill the process under memory pressure without invoking any lifecycle callback at all — a reliable exit-time flush is not buildable within those constraints, only a best-effort one, which is a different guarantee and was not attempted.

Closing a tab offers a three-way choice rather than only the original instant-discard confirm: **Discard without saving** (unchanged — a permanent `DeleteDraftAsync`, no recycle-bin entry), **Save settings first** (reveals an inline title field; confirming calls the existing `CreateSavedSettingAsync` with the draft's current model/prompt/system-instructions/source-file/result-count/destination-folder and only then deletes the draft, so a duplicate-title `NameConflictException` or other `SlopFactoryException` is shown inline and the tab stays open for the user to retry with a different title rather than losing the draft), and **Keep tab open** (cancel). No new domain/workspace method was needed for this — it composes `CreateSavedSettingAsync` and `DeleteDraftAsync`, both already used and tested elsewhere, from the GUI layer.

Session Recovery closes the two gaps the previous paragraph left open, without any schema change: since autosave already persists full draft state on every successful save, "the last successfully persisted revision" is just whatever is currently in SQLite, so there is no content/version snapshot to stage or reconcile — only whether an unsaved in-memory edit might exist needs tracking. `AppLibraryState.FlushForSuspensionAsync()` reuses the existing `Closing` event (and so `Generate.razor`'s existing subscriber) to provide the best-effort exit-time flush the previous paragraph called unbuildable-as-a-guarantee; it is wired from `App.xaml.cs`'s `window.Stopped`/`window.Destroying` handlers, and only proceeds if it can acquire `AppLibraryState`'s internal state lock without waiting, so it never races a real `SwitchAsync`/`RelinkAsync`/`AdoptCopyAsync`/`CloseInvalidLibraryAsync` already disposing the outgoing workspace. Separately, `AppLibraryState.MarkDraftDirty`/`ClearDirtyDraft` maintain a `DirtyDraftIds` set — one comma-joined `IAppPreferenceStore` key per library, holding only draft IDs, never content — reloaded whenever the active library opens (including on `InitializeAsync`, so a marker survives to the next app launch). `ScheduleAutosave` marks a draft dirty on every keystroke (a no-op write once already marked); `PersistCurrentDraftAsync` only clears the marker if no newer edit's token was issued while that save's I/O was in flight, so a save that was already stale by completion time can never erase the marker for an edit it didn't actually persist. `MainLayout.razor` surfaces a dismissible notice, following the same per-service-notice pattern as the queue/content-watch/scan-recommendation notices, whenever any marker is present for the currently open library.

## Generation queue and concurrency

`GenerationQueueService` (`src/Mellow.SlopFactory.Gui/Services/GenerationQueueService.cs`) schedules generation submissions instead of `/generate` awaiting the provider call inline. It deliberately does not add any asynchronous-job/polling state machine — neither `OpenAiProviderAdapter` nor `GenericOpenAiCompatibleProviderAdapter` exposes an actual submit-then-poll job API, so this is queueing and concurrency control layered on top of the existing synchronous `GenerateTextAsync`/`GenerateImageAsync` calls, not a redesign of `GenerationRecord`/`GenerationStatus`. It follows the same singleton-with-`Changed`-event convention as `ManagedContentWatchService` (a single `_gate` lock, a `Start()` subscribing to `AppLibraryState.Changed`, called once from `MainLayout.razor` alongside `ContentWatch.Start()`).

A `GenerationJobSnapshot` freezes exactly the fields the generation form edits (model ID, prompt, system instructions, source file, result count, destination folder, accepted improvement record ID) at the moment **Generate** is clicked, since the originating tab can be edited, switched away from, or closed while the job waits its turn — the service never reads live page state. It deliberately does **not** freeze the connection/provider type; `ExecuteAsync` re-resolves `Model`/`Connection` from the workspace at execution time, so a credential added while queued still works, and a model or connection that vanished by execution time (recycled while queued) produces a local failure outcome (`Record: null`, a `LocalErrorMessage`) rather than a fabricated `GenerationRecord`.

Each connection gets its own FIFO (`LinkedList<QueuedJob>`, not `Queue<T>`, so cancelling a queued-but-not-head job is an O(1) removal), with concurrency defaulting to 1 per connection but now user-adjustable (see below). A device-wide cap is enforced by a pump loop that scans an **append-only** `List<string> _connectionOrder` starting from a rotating `_cursor`, skipping any connection whose queue is empty or already at its per-connection concurrency limit, and only advancing the cursor past a connection once a job from it actually starts — never on every skipped scan step. This is what gives fairness: a connection with a deep backlog can start at most one job per pass through the full connection list before the cursor moves on, so it cannot consume every freed slot ahead of another eligible connection. Keeping the list append-only (never pruning a connection once its queue drains) avoids any reindexing hazard when a queue empties mid-rotation.

The device-wide cap itself is adjustable: `GenerationQueueService.DeviceCap` reads an `IAppPreferenceStore`-backed preference (`slopfactory.queue.devicecap`), falling back to the plan's stated defaults (`OperatingSystem.IsAndroid() ? 2 : 3`) when unset or unparsable, and `SetDeviceCap` clamps to `MinDeviceCap`/`MaxDeviceCap` (1–8 on Windows, 1–4 on Android) before persisting and immediately calling `Pump()` — so raising the cap while jobs are queued starts additional jobs right away rather than waiting for the next natural pump trigger (a job completing or a new enqueue). Lowering the cap never preempts an already-running job; it only limits how many *new* ones the pump loop is willing to start, consistent with the rest of the queue having no preemption concept. `LibrarySettings.razor` exposes this as a plain number input (mirroring the existing preview-cache-limit form) under a **Generation queue** panel — a device-level preference, not a per-library one, so it lives on the same settings page as the theme preference rather than anywhere library-scoped.

Per-connection concurrency is now adjustable too, via `GetConnectionCap(connectionId)`/`SetConnectionCap(connectionId, value)` — the exact same `IAppPreferenceStore` read-through/clamp/persist/`Pump()`-re-entry shape as `DeviceCap`/`SetDeviceCap`, just keyed per connection (`slopfactory.queue.connectioncap.{connectionId}`) instead of one fixed key, with the same 1–8/1–4 Windows/Android bounds. This is deliberately **not** a `Connection` schema field: like the device cap, it's a device-local preference about "how hard should *this device* hit this connection," not a fact that should travel with the connection across devices sharing a library, and not something this app can honestly assert on the provider's behalf — a per-connection limit is the user's own judgment about their account's rate limits, the same reasoning that already applies to the device-wide cap being user-configured rather than app-asserted. `Pump()`'s inner loop changed from a boolean "is any job running for this connection" check (`_runningPerConnection[connectionId]` only ever set to `0`/`1`) to a real counter compared against `GetConnectionCap(connectionId)`, incrementing on start and decrementing on completion; the outer round-robin/cursor logic is unaffected, since each `Pump()` call already loops until no connection has spare capacity. `ConnectionEdit.razor` exposes it in the existing "Advanced connection settings" section, only once the connection has a real, persisted ID to key the preference store by (unlike `TimeoutSeconds`, which is part of the connection's own create/update payload and available before first save) — its own small save action wired directly to the queue service, independent of the connection form's `OnValidSubmit`.

Cancelling a still-queued job removes it before its execution delegate is ever invoked and records `CancelledBeforeSubmission: true` with no `GenerationRecord` — the same "no history entry for work never actually submitted" contract `/generate`'s Cancel already had. Cancelling a running job just triggers the `CancellationTokenSource` the service created for it; the existing `OperationCanceledException` handling around the adapter call already creates no record either. On `AppLibraryState.Changed` (library switch or close), every still-queued job tied to the outgoing workspace is dropped outright and every running one is cancelled — `AppLibraryState` only ever holds one live, disposable workspace, and its switch/close methods already dispose the previous workspace *before* raising `Changed` (confirmed by reading `AppLibraryState.cs`), so a job's execution racing against a workspace mid-dispose is a real, pre-existing hazard already tolerated today by `ManagedContentWatchService` without special handling (a disposed SQLite connection fails a write cleanly rather than corrupting anything); `ExecuteAsync`'s catch clause includes `ObjectDisposedException` alongside `IOException`/`UnauthorizedAccessException`/`SlopFactoryException` so a losing race becomes a graceful local-error outcome instead of an unobserved-task crash.

`Generate.razor` no longer owns `_busy`/`_cancellation`/`_lastResult` for generation — `ActiveJobIds`/`RecentOutcomes` are computed properties that read the service instead, which is what lets a submission survive the page being disposed on navigation away from `/generate` and back: the durable side effect (the committed `GenerationRecord`) and the recent outcomes both live in the singleton service, not the page. The tab-close `×` button's busy-disable check covers any draft with one or more active jobs (`GetActiveJobIdsForDraft(draft.Id).Count > 0`), not just a single one. `MainLayout.razor` shows a small aggregate "N queued, M running" notice linking to `/queue`, mirroring the existing `IncomingImports`/`ContentWatch` notice pattern.

The same generation tab can now submit another run while one or more earlier runs from it remain active, per plan.md's "the same generation tab can submit another run while one or more earlier runs remain active." `Enqueue` no longer gates on a draft already having an active job — the single `Dictionary<string, string>` mapping one job per draft became `Dictionary<string, List<string>> _activeJobIdsByDraft`, and the single most-recent-outcome map became `Dictionary<string, List<GenerationJobOutcome>> _recentOutcomesByDraft`, capped at the 10 most recent per draft (newest first), matching plan.md's "ten most recent terminal run cards"; older terminal runs remain fully retained in generation history, never summarized away. The previous singular `GetActiveJobIdForDraft`/`GetLastOutcomeForDraft` accessors were kept as thin convenience wrappers (oldest active job / newest terminal outcome) specifically so every pre-existing single-job call site and test kept working unchanged; `GetActiveJobIdsForDraft`/`GetRecentOutcomesForDraft` are the new multi-run accessors. `Generate.razor` renders one **Runs** card per active/queued job (each with its own **Cancel** button, wired to `Queue.Cancel(jobId)` for that specific job) followed by one card per recent terminal outcome — cancelling one run never touches another submitted from the same tab, since cancellation was already keyed by job ID, not draft ID. The **Generate** button itself is no longer disabled while a run is active or queued; `FormDisabled` now tracks only `_busy`, a short-lived flag around the synchronous click-to-enqueue call, matching plan.md's "the action becomes available again even when that run is queued or active" — the previous behavior of disabling the whole form for a run's entire lifetime was what made concurrent runs from one tab impossible in the first place. There is no **View All Runs from This Tab** history-filter link yet, since `GenerationRecord` has no originating-draft-ID field to filter by — that remains open, tracked alongside the still-open generation-history/per-child-request-tracking item below.

`GenerationQueue.razor` (`/queue`) gives visibility across every open tab and connection at once: `GenerationQueueService.GetSnapshot()` returns a `GenerationQueueEntry` per non-terminal job (queued, with its position, or running), which the page groups by connection and enriches with the connection/model labels it already has loaded (the service itself only ever stores IDs, matching the immutable-snapshot design above). `ReorderQueuedJobs(connectionId, orderedJobIds)` follows the exact same whole-order-replace validation shape as `GenerationDraft`'s `ReorderDraftsAsync` — it takes the connection's complete reordered queued-job-ID list, rejects a mismatched set with `InvalidOperationException`, and rewrites the `LinkedList<QueuedJob>` in place — exposed in the UI as the same **‹**/**›** move-button pattern already used for tab reordering rather than drag-and-drop. Only jobs still queued on the *same* connection can be reordered relative to each other; a running job can only be cancelled, not moved, and there is no cross-connection priority.

`GenerationQueueService.EffectiveDeviceCap` layers a temporary reduction on top of the configured `DeviceCap`: it clamps to 1 while `IDeviceEnergyStateProvider.IsEnergySaverOn` is true, and `Pump()`'s cap check reads this instead of `DeviceCap` directly. Because `Pump()` only ever *starts* new jobs — it has no preemption concept anywhere in this service — this naturally satisfies "stops only new starts and never cancels active requests" without any special-casing: a job already running when energy-saver mode turns on keeps running to completion; only the *next* pump cycle is more restrictive. `IDeviceEnergyStateProvider` (Gui/Services) is a plain interface, same split as `ISecureCredentialStore`/`MauiSecureCredentialStore`: `MauiDeviceEnergyStateProvider` (not compiled into the test project) wraps `Microsoft.Maui.Devices.Battery.Default.EnergySaverStatus`/`EnergySaverStatusChanged` — no new package, since `Microsoft.Maui.Devices` is already a default MAUI global using and the Android build already registers Essentials' `EnergySaverBroadcastReceiver` in the manifest automatically. `Start()` subscribes to the provider's `Changed` event alongside `AppLibraryState.Changed`, re-running `Pump()` on every transition so a queued job starts the moment energy-saver mode clears rather than waiting for an unrelated queue event to trigger the next pump. `/queue` and `MainLayout.razor`'s aggregate activity notice both show **Energy Saver is limiting submissions to N at a time** while `EnergySaverCapActive` is true. True OS thermal-pressure detection remains open — MAUI has no built-in cross-platform thermal-state API comparable to `Battery`, and building a platform-specific one (Windows power-throttling APIs, Android `PowerManager.getCurrentThermalStatus`) was judged out of scope for this slice.

OS thermal-driven cap reduction and everything asynchronous-job/polling-related (**Submission Outcome Unknown**, **Monitoring Paused**, persisted cross-restart job resumption) all remain open, tracked in [milestone2.md](../../milestone2.md).

## Unified recycle bin

`RecycleBin.razor` (`/recycle-bin`) is the single restore/permanent-delete surface for every recyclable `RecycleBinItemKind` — `Folder`/`File`/`FileLink` from Milestone 1, and `Connection`/`Model`/`SavedSetting` added in this slice. `SqliteLibraryDatabase.GetRecycleBinEntriesAsync` hides an item from appearing as its own top-level entry while its parent is *also* currently recycled/pending-deletion, folding it into the parent's owned-counts instead (`NOT EXISTS (... parent.state IN (1,2))` for folders/files); the connection/model/saved-setting query blocks mirror this exactly (a model is never a separate entry while its connection is recycled too, and likewise for a saved setting under a recycled model or that model's connection), using `LEFT JOIN` for the saved-settings block since `saved_generation_settings.model_id` is nullable. This filtering is what makes the whole slice safe without inventing any new cascade logic: `RecycleConnectionAsync`/`RestoreConnectionAsync` and `RecycleModelAsync`/`RestoreModelAsync` already cascade fully to their dependents inside one DB transaction (already independently tested in `SavedGenerationSettingTests.cs`), so a connection and one of its own models/saved-settings can never appear as two independent selectable entries at once — `ProcessRecycleBinItemsAsync`'s restore/delete dispatch for the three new kinds is a thin `switch` calling straight through to those already-solid, already-tested `_database` methods (always the private `_database.X` call, never the public `LibraryWorkspace.X` wrapper, since the wrapper's own `RunMutationAsync` would deadlock against the mutation gate already held by the batch in progress).

`RecycleBinEntry` gained `OwnedModelCount`/`OwnedSavedSettingCount` as two new optional fields rather than overloading the existing folder/file/link counters, which stay folder/file/link-only. `GetRestoreBlockersAsync` gained matching cases for the three new kinds — Connection and Model both check recycled-state, an owning-parent-must-be-Active precondition (Model only), and an active-label conflict (a flat `SELECT EXISTS`, since connection/model/saved-setting uniqueness is library-wide, not parent-scoped, unlike folder/file names). **SavedSetting's case deliberately omits an owning-model-active check**: `RestoreSavedSettingAsync` itself never enforces one (a saved setting tolerates an inactive/missing model, matching its existing fallback-warning design elsewhere), so mirroring File/Folder's parent-active pattern here would have made the preview block restores that the underlying domain method actually allows.

Permanent deletion of a connection/model/saved-setting needed no `permanent_deletion_failures`-style retry tracking: unlike folder/file permanent-delete (which involves non-transactional managed-file I/O, hence that retry table), `PermanentlyDeleteConnectionAsync`/`PermanentlyDeleteModelAsync` are pure transactional SQL with no filesystem component, so a mid-cascade failure can't leave a partial state to retry — `RecycleBinEntry.DeletionFailure` stays `null` for these three kinds. One real behavior had to move, though: the old dedicated `Connections.razor` permanent-delete handler also cleaned up the deleted connection's secure-storage credential-ledger entries (`ISecureCredentialStore`), which `Infrastructure` cannot do (Gui-layer only) and which `CredentialReconciliationService` cannot retroactively catch (once a connection's row and its cascade-deleted ledger rows are gone, they can never be found again by that service's sweep). This cleanup now lives in `RecycleBin.razor` itself: before calling `PermanentlyDeleteRecycleBinItemsAsync`/`EmptyRecycleBinAsync`, it captures `GetCredentialLedgerSnapshotAsync()` filtered to the connection references in the pending batch; afterward, for each connection whose deletion actually succeeded, it removes every ledger revision's secure-storage entry, with each connection's cleanup wrapped in its own try/catch so one connection's secure-storage failure can't block cleanup for the rest of a batch (relevant for **Empty Recycle Bin**, which can delete many connections in one call).

## Generation-history recycle bin and file tombstoning

`GenerationRecord` was the last major entity with no `LibraryRecordState`/`recycled_at` lifecycle at
all (schema v26 adds `generation_records.state`/`recycled_at`, the exact shape `SavedGenerationSetting`
already has). `RecycleBinItemKind.GenerationRecord` slots into the existing unified recycle-bin
plumbing with no new cascade logic to invent, because plan.md is explicit that recycling or
permanently deleting a generation-history record touches neither its source nor result files in
either direction: `generation_results.generation_id`'s already-existing `ON DELETE CASCADE` only ever
removes the *link* rows when a generation record is permanently deleted, never the underlying `files`
rows, so `GetRecycleBinEntriesAsync`'s new query block needs no "hidden while parent recycled"
filtering at all (a generation record has no folder/connection/model relationship that would
double-list it) and `GetRestoreBlockersAsync`'s new case checks only recycled-state — there's no
title/label uniqueness constraint on generation records to conflict on, unlike every other named
entity. `GenerationHistory.razor`/`GenerationHistoryDetail.razor` each gained a **Recycle** action
matching the same "list/detail recycles, the bin restores/permanently-deletes" convention already
established for Connections/Models/SavedSettings; `GetGenerationHistoryAsync` gained a `WHERE state=0`
filter so a recycled record simply stops appearing on `/generation-history`, while
`GetGenerationRecordAsync(id)` deliberately stays unfiltered by state (matching `GetModelAsync`'s
"fetch regardless of state" precedent) so the bin's "view details" link still resolves a recycled
record's page.

File tombstoning closes the other half of the same milestone2.md item: previously, permanently
deleting a source or result file just silently cleared or dropped the reference (`source_file_id` to
`NULL`, or the `generation_results` row cascade-deleted entirely — the exact v25 fix from earlier this
session). Now both leave a snapshot of the file's former display name, media type and content hash
instead, mirroring the **already-existing, already-tested** `file_derivation_provenance` tombstone
pattern in `SqliteLibraryDatabase.DeleteFileRecordAsync` exactly: two more `UPDATE ... WHERE
source_file_id=$id`/`WHERE file_id=$id` statements run immediately before `DELETE FROM files`, in the
same transaction, using the already-fetched `FileRecord`'s `DisplayName`/`MediaType`/`ContentHash`.
Making the result side of this possible required changing `generation_results.file_id` from `ON
DELETE CASCADE` (the v25 fix, whose whole point was making permanent deletion not throw) to `ON DELETE
SET NULL` — the row now survives as a tombstoned placeholder instead of disappearing, since a deleted
row can't carry a tombstone. `FileIdentitySnapshot(DisplayName, MediaType, ContentHash)` — the exact
value type `file_derivation_provenance` already uses — is reused verbatim for both
`GenerationRecord.SourceFileTombstone` and the new `TombstonedResults` list, both purely additive:
`ResultFileIds` keeps its exact original meaning (currently-live result files only), so no existing
consumer (`GenerationHistory.razor`'s count, `GenerationHistoryDetail.razor`'s link list, every
existing test) needed any changes at all. An adversarial plan review before implementation
specifically re-verified the FK/cascade ordering (confirmed safe — SQLite applies `ON DELETE SET NULL`
as part of executing the `DELETE` statement itself, no deferral hazard) and the schema-version-bump
housekeeping (the routine `"schemaVersion": 25`→`26` replace across ~17 existing migration tests,
already the established mechanical step for every prior bump this session) before any code was written.

**Explicitly out of scope**, consistent with facts already established repeatedly this session (every
provider call is a synchronous in-process request/response, no async-job infrastructure exists):
plan.md's **Submission Outcome Unknown** recycling rules, **Refresh Provider Status**/**Output
Recycled** labeling, and **Reacquire Permanently Deleted Output** (which needs a persistent
provider-hosted result URL to re-download from later — neither adapter has one; both return inline
base64 content that's already committed as a local file at record-creation time). **Known, inherited
limitation, not newly introduced by this slice**: `DeleteFolderRecordAsync`'s batch descendant-file
delete already skipped the `file_derivation_provenance` tombstone update before this slice (confirmed
by reading it), and likewise skips the two new generation-tombstone updates — only the single-file
permanent-delete path (`DeleteFileRecordAsync`) is tombstoned, matching the scope the provenance
feature itself already settled for.

## Generation notifications

MAUI has no built-in cross-platform local-notification API (unlike `Battery`/`SecureStorage`/`Preferences`, all already used elsewhere in this app with no extra package). The community-standard package, `Plugin.LocalNotification`, was evaluated and rejected: its own README states "Only support **iOS** and **Android** for the moment" under Limitations even though its NuGet listing also carries a `net10.0-windows10.0.19041` target depending on `Microsoft.WindowsAppSDK` — a contradiction that couldn't be resolved from its docs, and Windows is one of this app's two target platforms. Notifications are hand-rolled instead, with **zero new NuGet packages**: `INotificationService`/`MauiNotificationService` (`src/Mellow.SlopFactory.Gui/Services/`) is one class split by `#if WINDOWS`/`#elif ANDROID` (the same single-file-with-conditional-blocks convention `PlatformFileActionService` already uses, rather than separate per-platform files). Windows uses `Microsoft.Windows.AppNotifications`/`.Builder` — already a transitive dependency of the MAUI Windows target, since this project already ships a packaged `Package.appxmanifest`; the implementation registers `AppNotificationManager.Default.NotificationInvoked` from the service's own constructor rather than from `Platforms/Windows/App.xaml.cs`'s `OnLaunched`, and deliberately skips the manifest COM-server/CLSID registration the official quickstart uses for the "app fully terminated, relaunched by tapping the notification" cold path — that case cannot occur here, because `GenerationQueueService` runs every job fully in-process with no persistence or background-service component, so a generation can only ever complete (and thus notify) while the app process is already alive. Android uses `AndroidX.Core.App.NotificationCompat`/`NotificationManagerCompat`, a `POST_NOTIFICATIONS` runtime permission requested only when the setting is enabled (via a `TaskCompletionSource`-based bridge on `MainActivity`, mirroring the existing `PickDocumentTreeAsync`/`CreateDocumentAsync` pattern), and a tapped notification's `PendingIntent` delivers the generation-record ID back through `MainActivity.OnCreate`/`OnNewIntent` to the DI-resolved `MauiNotificationService` — the same `IPlatformApplication.Current?.Services.GetService<T>()` bridge `Platforms/Windows/App.xaml.cs` already uses to reach `IncomingImportService` from platform activation code.

`GenerationQueueService` gained a `JobCompleted` event (`EventHandler<GenerationJobOutcome>`, raised in `RunJobAsync` for *every* finished job — success, failure, or cancellation — right alongside the existing generic `Changed`), giving a precise per-job completion signal instead of requiring a subscriber to diff `GetSnapshot()`/`GetActiveJobIdForDraft` against the generic event. `GenerationNotificationCoordinator` is the policy layer built on top: it gates on the device setting (`IAppPreferenceStore`, key `slopfactory.notifications.generationenabled`, default off), a new `IAppLifecycleState`/`AppLifecycleState` being non-foreground (wired from `Window.Activated`/`Deactivated`/`Resumed`/`Stopped` in `App.xaml.cs`, alongside the existing `Stopped`/`Destroying` handlers that already clear `ISensitiveRevealSessionService`), the outcome actually carrying a `GenerationRecord` (a local pre-submission failure or a cancellation never produced one, so there is nothing to summarize — no extra model-label resolution is needed for those paths), and `VisibleGenerationRecordId` not matching the record about to notify (set/cleared by `GenerationHistoryDetail.razor` on init/dispose, so its own page is never redundantly notified about itself). The coordinator deliberately does **not** call `INotificationService.Show` itself — it raises a plain `NotifyRequested(GenerationRecord)` event instead, leaving localizing the status text and actually showing the OS notification to `MainLayout.razor` (which already has `IStringLocalizer<UiStrings>` injected). This keeps the coordinator free of any UI/localization dependency, so it — like `GenerationQueueService` and `AppLibraryState` before it — stays fully unit-testable with plain fakes rather than needing a bUnit/localization harness. `MainLayout.razor` also subscribes to `INotificationService.Tapped` and navigates to `/generation-history/{id}`.

The **Submission Outcome Unknown**/**Submission outcome needs attention** alert variant from plan.md's Generation Notifications section is out of scope: this app has no async-job/reconciliation infrastructure (every provider call is a synchronous in-process request/response inside `GenerationQueueService.ExecuteAsync`), so that state can never occur. True OS thermal-pressure-style platform gaps aside, `MauiNotificationService`'s actual platform bodies have no automated test coverage (no bUnit/device harness in this repo, matching `MauiSecureCredentialStore`/`MauiDeviceEnergyStateProvider`) — verified only by the Windows/Android application builds and the manual test matrix.

`Connections.razor`/`Models.razor`/`SavedSettings.razor` keep only their active list and the **Recycle** action (recycling isn't part of "the bin," only restore/permanent-delete moved there); each now links to `/recycle-bin` instead of rendering its own recycled-list/restore/delete UI. While touching `ProcessRecycleBinItemsAsync`, its catch filter also gained `Microsoft.Data.Sqlite.SqliteException` — a pre-existing gap (not introduced by this slice) where `FileLink`'s restore/delete calls (already unwrapped, direct `_database` calls with no `LibraryValidationException` translation) could let a raw SQLite error abort an entire batch instead of being recorded as that one item's failure, unlike every other kind.
